# Release gate

ThreatVeil records an immutable exact-candidate release decision, signs its receipt, and can publish an App-owned GitHub check. The original GitHub OIDC Action remains available for a frozen single-property execution plan; it still fails closed unless qualified evidence identifies the exact workflow SHA. Its behavior was not loosened to introduce WARN mode.

The release-ledger API accepts a proof plan and a security-owned policy through `POST /v1/releases`. Policy modes are `OBSERVE`, `WARN` and `BLOCK`, with optional property-specific mode overrides. Security failures and missing evidence remain visible in all modes. WARN/OBSERVE decisions produce a non-blocking check when the effective result is WARN. A property configured for BLOCK can still block a release whose default mode is WARN. A qualified ALLOW produces success; effective BLOCK produces failure; effective WARN produces neutral. Configure GitHub branch protection to require the check from the intended App when adopting blocking mode.

Exceptions are separate immutable requests and approvals, scoped to an exact plan, candidate and property set. The release records both the underlying outcome and the effective action. Approved break-glass does not erase the original FAIL. Current receipt reads and check delivery reassess authorization and evidence; a historical ALLOW remains in the ledger even when its current authorization is blocked.

## GitHub App setup

1. Create a GitHub App and install it on the intended repositories. The App needs Checks write permission and the metadata GitHub requires. Subscribe to push, installation and installation-repository lifecycle events. Configure the public webhook endpoint as `/v1/webhooks/github` (or the corresponding API relay path).
2. Configure `TV_GITHUB_APP_ID`, `TV_GITHUB_PRIVATE_KEY` and `TV_GITHUB_WEBHOOK_SECRET` through the deployment secret boundary. Use a strong random webhook secret. Configure a valid HTTPS `TV_WEB_ORIGIN` for the receipt details link.
3. Register the existing operator-reviewed repository binding with `threatveil operator github-bind`: numeric repository and owner IDs, exact trusted workflow/ref, active security owner and authorized target/observer execution template. This remains the authority for repository-to-organization routing.
4. As a workspace security owner, call `POST /v1/github/app/installations` with `repository_id` and `installation_id`. ThreatVeil verifies the real installation, App identity, owner, selected repository and Checks permission through GitHub before storing the installation review.
5. Establish the candidate fingerprint and proof plan, perform the required re-proof, and create a release. An installed exact Git candidate is queued in the same transaction as the immutable release and signed receipt. `POST /v1/github/releases/{release_id}/publish` can idempotently queue a previously created release after installation.
6. Run the existing maintenance reconciliation loop. `reconcile_github_checks()` processes durable check-delivery records. Inspect `/v1/github/check-deliveries` for delivery status and failures; `/v1/github/app/installations` shows local enablement. Only a confirmed GitHub response creates a `github_check_publication` evidence record.

Authenticated pushes create immutable `github_change_event` records, exposed at `/v1/github/change-events`, with exact native Git SHA, repository/ref, body digest and `REPROOF_REQUIRED`. They establish a change signal. They do not claim that staging has deployed that SHA, synthesize qualified evidence, automatically execute customer targets, or manufacture a complete model/tool/prompt fingerprint. Use the existing authorized execution path to establish those facts.

## Authentication and retry behavior

Webhook authentication follows [GitHub's HMAC-SHA256 protocol](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), comparing signatures in constant time over the exact body bytes before JSON parsing. Duplicate JSON keys are rejected. GitHub delivery headers are not signed; replay claims therefore bind the authenticated body digest. Push routing checks the registered numeric repository ID, owner ID, full repository name, branch, live candidate SHA and installation ID. Suspension, deletion and repository removal revoke local installation approval; unsuspend/add events never silently restore an old review.

The App exchanges a short-lived RS256 JWT for an [installation token scoped to the intended repository and Checks permission](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app). Tokens are not persisted in the delivery queue. Requests use a fixed GitHub API origin, bounded timeouts and no redirect or ambient proxy inheritance.

Each release has one deterministic durable outbox identity. Workers claim it with a fence and expiry. Immediately before a GitHub check write, the worker durably records that a side effect may occur. Check reconciliation matches the exact SHA, App ID, check name and release external ID. A lost create response is recovered by finding and updating that check. If creation remains ambiguous and no matching check can be found, the worker refuses to create a possible duplicate. Retries are bounded; after ten claims the queue requires operator attention. This is conservative recovery, not a claim of distributed exactly-once GitHub delivery.

Before publishing, ThreatVeil rechecks the current release assessment, approved properties, evidence and exception applicability, repository owner authority and active installation. It holds its system/repository locks through the bounded publication attempt. A downgraded current check explicitly distinguishes its action from the signed historical action. The newest delivered decision for a repository is scheduled for reassessment after five minutes; actual delay also depends on scheduler cadence, backlog and provider availability. Explicit publish requests refresh that decision immediately in the queue. Older decisions are marked superseded and are not continuously polled. Subsequent external changes are not atomically synchronized with GitHub; consumers must obtain a fresh decision for a later deployment. A successful receipt or check never certifies indefinite future behavior.

## Verified scope and external acceptance

Local tests exercise the real tenant-isolated PostgreSQL lifecycle, immutable receipt references, body-digest replay protection, revoked installation/owner authority, cross-tenant rejection, claim fences, WARN/BLOCK projection and lost-response reconciliation. Only the external GitHub API is substituted in those tests. Protocol tests independently validate signatures, exact-SHA mapping, installation permissions, App JWTs, scoped token requests and rejection of ambiguous duplicate checks.

A real GitHub App registration, installed customer repository, HTTPS deployment, delivery reconciliation schedule and required-check branch protection need live acceptance. This implementation has not established those external facts by passing local tests. GitHub environment/deployment-protection approval hooks and automatic execution from pushes are not implemented; the App currently supplies change intake and the exact-release Checks surface.
