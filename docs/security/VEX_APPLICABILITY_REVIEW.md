# Python runtime vulnerability applicability review

Review date: 7 September 2026. Status: six exact absent-component dispositions are enabled through a guarded OpenVEX generator. Raw findings remain retained; the guarded release gate passes only after all runtime, image, package and expiry checks. This review applies only to the image and source digests in [the scan record](SCAN_RESULTS_2026-09-07.md), with vetted hosted adapters and no customer code installation. The enforced review expiry is 14 September 2026. Every image change requires fresh digest-bound runtime assertions and scans; dependency, adapter or SQLite data-path changes also require applicability review.

The final runtime retains official CPython 3.13.15 and required native libraries on pinned distroless cc Debian 13. The assembler preserves base libraries and adds package metadata for copied libraries; it does not erase inventory to make scanning pass. Raw Trivy output reports six HIGH package/advisory records across five unique CVEs, zero CRITICAL and zero application-package findings. The two actual SQLite vulnerabilities were fixed with upstream 3.53.4; no SQLite VEX exception is allowed.

These are package-source associations: Debian tracks vulnerabilities against source packages that produce multiple binary packages. The narrower delivered files matter. A future addition of CLI tools, debug images, arbitrary code, mounted utilities or installable plugins invalidates these dispositions. Non-root execution alone is not the evidence of absence.

## SQLite was patched, not excepted

[CVE-2026-11822](https://security-tracker.debian.org/tracker/CVE-2026-11822) and [CVE-2026-11824](https://security-tracker.debian.org/tracker/CVE-2026-11824) affect malformed FTS5 database/page handling before 3.53.2. The runtime now loads upstream SQLite 3.53.4. Its source archive and `sqlite3.c` are checked against the publisher's SHA3-256 values, then built as a shared library in a separate compiler stage. Compiler tools do not ship. The release gate checks the actual mapped library path, source/binary hashes, version, and a real FTS5 insert/query. The FTS5 feature remains enabled. [Upstream release](https://www.sqlite.org/releaselog/3_53_4.html), [publisher download checksums](https://www.sqlite.org/download.html).

The old Debian SQLite binary and its package record are not delivered. The upstream replacement has its own CycloneDX component with PURL, CPE, source origin and binary hash; `include_native_sbom.py` also includes it in exported SPDX. It is not presented as an unmodified Debian package. Stock Trivy/Syft cataloguing did not automatically retain this generic native component, so explicit inclusion is required. Inventory does not create comprehensive native vulnerability-feed coverage: the pinned upstream release and known-fix checks must be reviewed on updates and when new SQLite advisories appear. Do not infer complete SQLite CVE coverage from a clean generic-package scan.

## Evidence and enforcement

Local private evidence is under `.local/security-reports/python-frozen-gate/`: `raw.json`, `filtered.json`, `trivy.cdx.json`, `image.openvex.json`, `sqlite.cdx.json`, `applicability-evidence.json`, and `decision.json`. The [scan record](SCAN_RESULTS_2026-09-07.md) identifies exact tested images. These artifacts contain synthetic/software inventory only.

`infra/scripts/image_security_gate.py` performs a fresh raw scan, obtains Trivy's exact OCI image PURL/digest, checks that the runtime and final scan refer to that same image, and creates subcomponent statements for only the listed Debian package names and exact versions. The generator verifies missing infocmp/mount/nsenter and mount helpers, absence of libmount, non-root execution, no shell/package manager, the exact CPython version, and the patched SQLite conditions. A failed prerequisite emits no VEX. Expiry is checked before statement issuance. The final scanner's removed-record set must exactly equal the permitted records; any other filtered finding causes failure. New findings remain blocking.

Negative local checks confirmed that a wrong image digest leaves all six findings blocking, a harmless `/usr/bin/mount` marker prevents VEX issuance, and an older SQLite runtime prevents VEX issuance. This is verified build-pipeline behavior, not remote attestation against a compromised builder or image able to falsify its own execution. VEX must be regenerated and checked for each exact release image. The generated statements are local artifacts, not signed attestations or already-published registry metadata.

No blanket ignore or ignore-unfixed mode is enabled. CI and dev delivery retain both raw and filtered results. The only current statements use `vulnerable_code_not_present` for exact library subcomponents in an exact image; no SQLite exception exists. See [Trivy's OpenVEX subcomponent documentation](https://github.com/aquasecurity/trivy/blob/main/docs/guide/supply-chain/vex/file.md).
