# Integrity Launch

Integrity Launch is the scoped path from a prepared system to a working release-integrity installation. The workspace records scope, reviewed security properties, target/collector readiness, founder effort and append-only milestone events. Legacy Gauntlet record keys remain readable for compatibility; customer-facing copy uses Integrity Launch.

A synthetic setup can demonstrate the loop but cannot establish installation. LIVE_WARN_DELIVERY_VERIFIED requires a confirmed GitHub publication linked to the launch system, matching release/receipt, current applicability and active installation/binding. A queued check, screenshot, manually completed checklist or local demonstration cannot satisfy that milestone. Paid conversion comes from authoritative account/payment state; a pilot allowance never counts as paid.

Start with one consequential workflow and an agreed budget. Review the property and target boundary, qualify independent observation, establish a failing baseline and useful fix, then install WARN mode in the real release path. Review actual release outcomes before adopting BLOCK and required-check enforcement. Record founder/customer setup time, time to useful evidence, repeat release and second-system work from real events.

Offers are configured protected-system scope with explicit allowances; no speculative public dollar anchors are published. Purchase/payment, real onboarding speed, recurrence and expansion remain unproven until the corresponding customer events occur.

## Product-backed deliverables (category-complete wave)

An Integrity Launch is an installed-product activation program, not consulting. *Give us one consequential autonomous workflow. ThreatVeil establishes the critical assurance boundary, connects the relevant change and evidence sources, and keeps the current security conclusions visible as the system changes.*

It delivers:

- one protected system and workflow
- 3–5 critical claims, defined in business language (`claim-definitions`) and made executable
- a qualified observer and a baseline
- connected change monitoring with reviewed dependency mappings
- current clearance and a Current Assurance Passport
- an Assurance Gate consumer where supported (CI first)
- 30 days of change and assurance history

Production enforcement is not promised without a qualified enforcer.
